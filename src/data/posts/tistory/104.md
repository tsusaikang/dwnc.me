<p data-ke-size="size16">처음 깃허브 레포지토리를 열었는데 server/, client/ 같은 폴더명이 보인다? 저도 “어? 클라이언트라면 사용자 PC 아닌가? 왜 서버에 client 코드가 있지?” 하고 당황한 적이 있습니다. 사실 이 폴더들은<b> ‘어디서 돌 명령인가’를 구별</b>하기 위한 라벨일 뿐입니다. </p>
<blockquote data-ke-style="style1">
<p data-ke-size="size16"><b>코드가 ‘실행된다’는 건 뭐죠?</b><br />컴퓨터가 파일에 적힌 명령(코드)을 한 줄씩 읽어 ‘행동’(연산·저장·출력)을 수행한다는 뜻입니다. 우리가 웹브라우저 주소창에 example.com 을 치는 순간에도, 서버라는 컴퓨터 안쪽에서 “누가 왔네? HTML 보내줘!”라는 명령이 <b>순서대로 실행</b>됩니다.</p>
</blockquote>
<p data-ke-size="size16">아래에서 아주 기초부터 차근차근 풀어봅니다.</p>

<h2 data-ke-size="size26">1. 두 폴더가 가리키는 ‘실행 장소’</h2>
<p data-ke-size="size16">폴더 이름 명령을 읽어‑돌리는 주체 하는 일(예시)</p>
<table style="border-collapse:collapse;width:100%" data-ke-align="alignLeft" data-ke-style="style13">
<tbody>
<tr>
<td style="width:10.9302%"><b>폴더 이름</b></td>
<td style="width:34.8837%"><b>코드를 읽고 실행하는 주체</b></td>
<td style="width:53.9535%"><b> 하는 일(예시) </b></td>
</tr>
<tr>
<td style="width:10.9302%"><b>server/</b></td>

<td style="width:53.9535%">• 인터넷 요청 수신• 데이터베이스 읽기/쓰기• 첫 화면 HTML 미리 만들기(SSR)</td>
</tr>
<tr>

</tr>

<blockquote data-ke-style="style1">
<p data-ke-size="size16">브라우저도, 서버도 결국 ‘컴퓨터 프로그램’입니다.<br />server 코드는 <b>서버용 프로그램이 읽어 실행</b>하고, client 코드는 <b>브라우저라는 프로그램이 읽어 실행</b>합니다.</p>
</blockquote>
<p data-ke-size="size16">따라서 폴더를 나누는 목적은 “같은 컴퓨터 안이라도 누가 읽어야 할지 헷갈리지 않게” 하기 위해서예요.</p>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">2. 왜 서버에도 자바스크립트가 있을까? — Node.js 등장 스토리</h2>
<p data-ke-size="size16">옛날 웹</p>
<ul style="list-style-type:disc" data-ke-list-type="disc">
<li><b>브라우저</b> : 자바스크립트(JS)</li>
<li><b>서버</b> : PHP, Java, Ruby … 언어 제각각</li>
</ul>
<p data-ke-size="size16">2009년 <b>Node.js</b> 등장</p>
<ul style="list-style-type:disc" data-ke-list-type="disc">
<li>구글 크롬 엔진(V8)을 따로 꺼내 <b>“서버 프로그램”</b> 으로 실행</li>
<li>서버도 JS 사용 → 프런트·백엔드 한 언어</li>
</ul>
<blockquote data-ke-style="style1">
<p data-ke-size="size16"><b>결과</b> : 프로젝트 폴더 하나에 server (JS) + client (JS) 가 공존하는 풍경이 기본이 됐습니다.</p>
</blockquote>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">3. ‘언제 어디서 화면을 그리나?’ CSR vs SSR</h2>
<h3 data-ke-size="size23">3‑1 CSR (Client‑Side Rendering)</h3>
<ol style="list-style-type:decimal" data-ke-list-type="decimal">
<li>서버는 빈 index.html 과 큰 JS 파일 하나만 보냄.</li>
<li>사용자의 브라우저가 그 JS 파일을 <b>실행</b>→ 화면 첫 펼침.</li>
<li>장점: 서버 단순. 단점: JS 다운로드·실행 지연.</li>
</ol>
<h3 data-ke-size="size23">3‑2 SSR (Server‑Side Rendering)</h3>
<ol style="list-style-type:decimal" data-ke-list-type="decimal">
<li><b>서버 프로그램(Node.js)</b> 가 React 컴포넌트를 <b>실행</b>→ 완성 HTML 발송.</li>
<li>브라우저는 화면을 ‘번쩍’ 보고 시작.</li>
<li>이후 클릭·스크롤 등의 변화는 클라이언트 JS 파일이 담당.</li>
</ol>
<blockquote data-ke-style="style1">
<p data-ke-size="size16">즉 <b>SSR 방식</b>이라도 JS 번들(클라이언트 코드)은 꼭 필요합니다.<br />서버가 초기 HTML만 대신 ‘실행’해서 만들어줄 뿐, 사용자와 직접 상호작용하는 부분은 브라우저 JS가 ‘실행’합니다.</p>
</blockquote>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">4. 물리적으로 한 서버에 두고 폴더로만 나누는 이유</h2>
<pre class="axapta"><code>my‑app/
├─ server/   # 백엔드 JS 소스
├─ client/   # React 등 프런트 소스
└─ build/    # 번들된 JS/CSS (브라우저용)
</code></pre>
<ul style="list-style-type:disc" data-ke-list-type="disc">
<li><b>배포</b> : Node.js 프로세스(= 서버 코드) + build/ 정적 파일을 하나의 호스팅(AWS EC2, Vercel 등)에 올립니다.</li>
<li><b>성능</b> : 필요하면 build/ 폴더만 CDN에 복사(전 세계로 캐싱).</li>
</ul>
<h3 data-ke-size="size23">정말 서버를 둘로 나누는 경우는?</h3>
<ul style="list-style-type:disc" data-ke-list-type="disc">
<li>유튜브·넷플릭스 같은 초대형 트래픽 — 정적 파일 CDN 분리</li>
<li>대기업 조직 분업 — 프런트·백엔드가 서로 배포 스케줄 독립</li>
</ul>
<p data-ke-size="size16">99 % 사이드 프로젝트·스타트업에선 <b>한 서버 + CDN</b> 구조가 기본입니다.</p>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">5. 헷갈릴 때 이렇게 생각하면 끝!</h2>
<ol style="list-style-type:decimal" data-ke-list-type="decimal">
<li><b>‘코드를 실행한다’</b> = 어떤 프로그램(서버나 브라우저)이 파일을 읽고 명령을 순서대로 수행한다.</li>
<li><b>server 코드</b> → 서버용 프로그램(Node.js 등)이 실행하는 명령.</li>
<li><b>client 코드</b> → 브라우저 프로그램이 실행하는 명령.</li>
<li>폴더명은 실행 주체를 표시하는 라벨일 뿐, 물리 서버 위치를 말하지 않는다.</li>
</ol>
<blockquote data-ke-style="style1">
<p data-ke-size="size16">앞으로 레포지토리를 볼 때 “폴더 = 서버”가 아니라 <b>“폴더 = 이 명령은 어느 프로그램이 읽을까?”</b> 로 이해해 보세요. 구조가 한층 깔끔하게 보입니다 🙂</p>
</blockquote>
