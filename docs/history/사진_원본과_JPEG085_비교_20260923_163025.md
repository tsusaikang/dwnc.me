# 업로드된 원본과 JPEG 품질 0.85 비교

2026-09-23 사용자가 기존 약 10MB 사진 여러 장에 대해 원본·압축본의 용량 비교표와 화살표키로 넘기는 비교 화면을 요청했다. 운영 파일 교체나 압축 설정 변경은 요청 범위에 포함하지 않는다.

## 자료와 변환

이번 작업에서 공개 글 `/posts/600`의 현재 HTML을 새로 조회하고 본문 사진 9개 중 순서 1·3·6·9 네 장을 내려받았다. 과거 이관 덤프나 이전 내려받은 사진을 입력으로 사용하지 않았다. 여기서 원본은 현재 서버에 올라가 있는 파일이며 최초 카메라 원본과 동일하다는 뜻은 아니다.

현재 `src/lib/admin-image-upload.ts`의 `imageUploadScript`와 `normalizeUploadImage`를 그대로 Chromium 153.0.8010.12에서 실행했다. 품질값 0.85, 최대 16,000,000픽셀, 작은 입력의 팽창 방지 등 실제 업로드와 같은 정책이다. 로컬 비교용 결과만 만들었으며 운영 업로드·사진 교체·삭제는 하지 않았다. 브라우저별 JPEG 인코더 차이로 동일 품질값의 결과가 항상 같은 바이트가 되는 것은 아니다.

## 측정 결과

MB는 1,000,000바이트다. 세로 사진 3개는 3072×4080, 가로 사진 1개는 4080×3072이며 모두 12,533,760픽셀이다. 네 장 모두 크기 축소 없이 JPEG 재인코딩만 수행됐다.

## 산출물과 보존

모든 사진과 비교 화면은 Git 제외 `migration/private/photo_comparison_20260923/`에 있다. `source.json`은 이번 조회 주소와 입력 크기, `results.json`은 측정값, `data.js`는 화면용 데이터, `images/`는 원본과 압축본이다. `prepare-comparison.mjs`는 실제 업로드 코드로 결과를 만든 로컬 처리 스크립트다. 비교 화면의 납품 파일명은 `photo-comparison_20260923_163025.html`이다.

메인은 최신 운영 입력 조회·로컬 변환·통합·화면 확인을 맡고, 하위 에이전트는 독립적인 비교 화면을 작성했다. 공식 기록만 Git에서 관리하며 사진이나 개인 산출물을 공개 저장소에 넣지 않는다.

## 화면 확인

실제 Chromium에서 네 행의 측정값, 좌우 방향키의 원본→JPEG→다음 사진 순서와 역방향 이동, Space의 같은 사진 전환, 전환 전후 스크롤 위치 보존, 100%·200% 너비, 화면 맞춤, 390px 화면과 실행 오류 없음을 확인했다. 화면 맞춤 미리보기의 사진 및 표도 시각 확인했다. 기본 표시는 100%(이미지 1픽셀=CSS 1픽셀)이며 고해상도 디스플레이의 물리적 픽셀과 구분해 안내한다. 비교 파일은 인터넷에 배포하지 않고 로컬에서만 제공한다.
