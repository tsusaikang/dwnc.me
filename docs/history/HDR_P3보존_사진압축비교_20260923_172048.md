# HDR·P3를 유지한 사진 압축 비교

2026-09-23 사용자가 색역과 HDR 표현을 유지한 압축 결과로 다시 비교하도록 요청했다. 동일한 네 사진의 로컬 비교본과 비교 화면을 완성했다. 편집기 운영 코드·서버 사진·글·공개 상태는 변경하지 않았다.

## 입력과 방법

현재 공개 글 `/posts/600`을 자체 브라우저로 다시 읽고, 앞선 비교의 네 파일명·사진 주소가 계속 참조됨을 확인했다. 단순 HTTP 조회는 403이었고 자체 브라우저에서는 정상 조회됐다. 동일 표본의 연속 비교이므로 앞서 실제 서버에서 내려받은 원본 바이트를 입력으로 유지했다. 이번에 서버 파일 바이트의 재다운로드·동일성까지 확인했다는 뜻은 아니다. 과거 이관 덤프는 사용하지 않았다.

Google libultrahdr 1.4.0의 공식 API로 기본 JPEG·원본 gain map·ICC·HDR 수치 정보를 읽었다. Pillow 12.3.0으로 P3 RGB 색값을 색 공간 변환 없이 quality 85, 4:2:0, optimized Huffman 설정으로 다시 압축하고 원본 ICC를 유지했다. 원본 gain map의 JPEG 코딩 데이터를 그대로 사용하며 공식 API-4로 ISO 21496-1·XMP·MPF 정보를 재작성해 결합했다. 원본의 모든 부가 영역을 단순 복사한 방법이 아니다. 해상도·방향은 유지했으며 방향값 외 카메라 EXIF·디버그 정보는 옮기지 않았다.

이는 로컬 네이티브 도구로 만든 비교 실험이다. 브라우저 편집기에 해당 처리기를 연결하거나 모바일 성능·메모리·모든 이미지 형식 호환성을 시험한 결과가 아니다. 기존 Canvas 품질 0.85와 새 인코더의 품질 85는 같은 품질 척도나 동일 바이트 조건이 아니므로 차이를 HDR 데이터 크기만으로 해석하지 않는다. 재압축한 기본 JPEG는 손실 압축이므로 최종 HDR 픽셀이 원본과 완전히 같다는 뜻도 아니다.

공식 참고: [libultrahdr 1.4.0](https://github.com/google/libultrahdr/releases/tag/v1.4.0), [공식 API](https://github.com/google/libultrahdr/blob/v1.4.0/ultrahdr_api.h).

## 측정 결과

MB는 1,000,000바이트. 세로 세 장은 3072×4080, 가로 한 장은 4080×3072로 세 버전의 해상도가 모두 같다.

| 사진 | 원본 bytes | HDR·P3 유지 bytes | 원본 대비 감소 | 기존 sRGB·SDR bytes |
|---|---:|---:|---:|---:|
| 1 | 9,060,863 | 2,451,589 | 72.9% | 1,622,557 |
| 2 | 8,642,354 | 2,264,343 | 73.8% | 1,458,941 |
| 3 | 9,688,660 | 2,753,341 | 71.6% | 1,890,672 |
| 4 | 11,240,229 | 3,428,075 | 69.5% | 2,273,622 |
| 합계 | 38,632,106 | 10,897,348 | 71.8% | 7,245,792 |

네 출력 모두 원본 P3 ICC가 바이트 단위로 같고, gain map의 JPEG 코딩 데이터·디코딩 픽셀·해석에 필요한 수치가 같다. 원본과 출력 모두 공식 디코더로 Display-P3 linear RGBA half-float HDR 디코딩에 성공했다. ISO·XMP HDR 정보도 확인했다. 실제 사용자 화면의 밝기·색감·선명도 체감은 사용자의 비교로 판단하며 일반 스크린샷을 HDR 밝기 재현의 측정 증거로 사용하지 않는다.

## 산출물과 화면 확인

사진·스크립트·의존성·결과는 Git 제외 `migration/private/photo_comparison_20260923/`에만 있다.

- `photo-hdr-comparison_20260923_172048.html`: 새 3종 비교 화면. 원본→HDR·P3 유지→기존 SDR 순서로 방향키 전환, Space는 원본↔HDR 유지본 전환. 100%·200%·화면 맞춤과 같은 위치 유지, 사진별·합계 용량표.
- `data-hdr-comparison.js`, `results-comparison-hdr.json`: 새 비교 데이터. 이전 비교 파일은 유지했다.
- `hdr-preserved/photo-{1..4}-hdr-q85.jpg`: HDR·P3 유지 압축본.
- `hdr-preserved/results-hdr.json`, `README.md`, `make_comparison.py`: 검증 결과와 재현 방법. 네이티브 라이브러리와 중간 기본 JPEG도 같은 디렉터리에 있다.
- `hdr-source-refresh.json`: 현재 공개 글의 대상 사진 참조 재확인 범위.

기존 로컬 서버의 `http://127.0.0.1:8768/photo-hdr-comparison_20260923_172048.html`로 제공했다. 메인이 사용자 전용 자체 브라우저에서 실제 12개 이미지가 모두 열리고 원래 해상도로 표시되는지, 방향키·Space 전환, 100%·200%·맞춤, 동일 위치 보존, 용량표·합계, 콘솔 오류 없음을 확인했다. 파일은 `<img>`로 직접 표시하며 Canvas로 다시 그리지 않는다. 첫 사진의 원본·100% 상태로 돌려 사용자에게 보여줬다. 변환과 화면 작성은 각각 하위 에이전트가 맡았다.

## 남은 판단과 범위

사용자의 육안 비교가 다음 단계다. 운영 편집기의 HDR·색역 보존 처리는 아직 미적용이며, 기존 업로드 방식과 서버 사진은 그대로다. 결과가 적절하면 별도 후속 구현에서 브라우저 처리 경로·실제 파일 업로드를 확인해야 한다. 이번 문서 동기화는 기능 변경을 포함하지 않는다.

## 후속: 같은 조건의 품질 80 비교

사용자는 품질 85에서 밝기 외 차이가 거의 느껴지지 않는다며 품질 80 비교를 요청했다. 밝기 차이의 원인은 이번 요청에서 해결됐다고 판단하지 않는다. 현재 공개 글의 네 파일명·참조 주소를 자체 브라우저로 다시 확인했고, 같은 로컬 원본 네 장에서 직접 품질 80 결과를 생성했다. 85 결과를 다시 압축하지 않았으며, 같은 인코더·서브샘플링·HDR 결합·부가정보 처리에서 기본 JPEG 품질값만 85→80으로 바꿨다.

| 사진 | HDR·P3 품질 85 bytes | HDR·P3 품질 80 bytes |
|---|---:|---:|
| 1 | 2,451,589 | 2,151,297 |
| 2 | 2,264,343 | 1,989,049 |
| 3 | 2,753,341 | 2,432,876 |
| 4 | 3,428,075 | 3,073,989 |
| 합계 | 10,897,348 | 9,647,211 |

품질 80은 원본 합계 대비 75.0%, 품질 85 대비 추가 1,250,137바이트(11.5%) 감소했다. 네 장 모두 해상도·P3 ICC·원본 gain map 코딩 데이터와 픽셀·HDR 수치 정보를 보존했고 실제 HDR 디코딩에 성공했다. 기존 원본·85 파일은 변경되지 않았다.

같은 비공개 로컬 폴더에 `hdr-preserved/make_comparison_q80.py`, `hdr-preserved/results-hdr-q80.json`, `hdr-preserved/photo-{1..4}-hdr-q80.jpg`를 추가했다. 새 비교 화면은 `photo-hdr-q80-comparison_20260923_173305.html`, 데이터는 `data-hdr-q80-comparison.js`다. Space는 85↔80 직접 전환, 방향키는 원본→85→80 순서이며, 기존 SDR 비교는 별도 링크로 유지한다.

메인이 자체 브라우저에서 네 품질 80 이미지의 실제 로딩·해상도, Space·방향키 전환, 같은 위치 유지, 화면 맞춤과 100%, 용량 합계를 확인했다. 콘솔 오류가 없었으며 첫 사진의 품질 80·100% 상태로 비교 화면을 열어 두었다. 운영 편집기와 서버 사진은 변경하지 않았다.
