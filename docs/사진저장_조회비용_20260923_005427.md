# 사진 저장과 조회 비용 참고

2026-09-23 운영 관리 화면·이번 D1 메타데이터 조회·현재 소스와 공식 요금표를 확인한 읽기 전용 설명이다. 후속 사진 크기 비교는 로컬 이관 보존본의 헤더·메타데이터 집계와 이번 운영 공개 표본을 따로 구분했다. 요금제·정책·기능·운영 콘텐츠를 변경하지 않았다. 금액은 USD이며 아래 예시는 세금·환율을 제외한 단순 추정이다.

## 지금은 얼마를 사용하고 있나

현재 Workers는 Free, 사진 저장소는 R2 Standard다. 계정 전체 R2 사용량은 6.12GB이며 이번 청구 기간(2026-08-25~09-25)의 화면상 청구 대상 금액은 $0이다. Class A 작업은 약 8.43천 회, Class B 작업은 약 116.77천 회로 표시됐다. 이는 조회 시점의 누계이며 최종 청구서가 아니다.

| 저장소 구분 | 현재 크기 | 해석 |
|---|---:|---|
| 운영 native | 약 1.43GB | 약 2.75천 객체. 이관 자료도 포함하므로 신규 업로드 사진 수가 아니다. |
| 운영 public | 약 2.35GB | 이관 공개 자료를 포함한다. |
| 시험 public | 약 2.35GB | 시험용 자료도 같은 계정 저장 요금에 합산된다. |

개별 표시값을 반올림해 더하면 전체 표시값과 약간 다를 수 있다. 무료 용량은 저장소마다 따로 주어지는 것이 아니라 계정에서 합산된다.

## 업로드하면 원본을 그대로 저장하나

현재 블로그는 브라우저가 업로드 요청으로 전달한 파일의 바이트를 그대로 R2에 저장한다. 서버에서 사진 크기 축소·압축·화질 변환을 하지 않는다. 따라서 사진 파일 하나가 10MB라면 저장 공간도 대략 10MB가 늘어난다. 휴대폰이나 브라우저가 보내기 전에 파일을 바꿨는지는 별개다.

D1에는 사진 파일 자체 대신 연결 정보 등 메타데이터를 저장한다. 현재 파일당 한도는 25MiB(26,214,400바이트)이며, 편집기의 표시 너비 조절은 CSS 표현을 바꾸므로 저장 파일의 크기를 줄이지 않는다.

이번 D1 조회에서 확인한 최근 업로드 기록은 다음과 같다. **업로드 기록 수이며 현재 첨부 수나 서로 다른 사진 수를 뜻하지 않는다.**

| 글 번호 | 업로드 기록 | 합계 | 파일 크기 참고 |
|---|---:|---:|---|
| #599 | 2개 | 12,284,376바이트 | 각 6,142,188바이트 |
| #600 | 9개 | 93,636,315바이트 | 최소 8,642,354·최대 14,718,822바이트, 평균 약 10.40MB |
| #601 | 3개 | 493,302바이트 | 평균 약 0.16MB |

사용자가 보고 있는 #600의 이번 업로드 기록은 9개·약 93.6MB로, 사진 하나 평균 약 10.4MB다. 운영 공개 본문 DOM에서도 사진 9개를 확인했지만 개별 파일 경로까지 대조한 것은 아니므로 업로드 9개가 현재 사진과 각각 동일하다고 단정하지 않는다. 아래 비용 예시는 계산을 쉽게 하려고 사진당 10MB를 사용한다.

## 사진이 늘면 저장 요금은

R2 Standard 무료분은 매월 저장 10GB-month, Class A 100만 회, Class B 1,000만 회다. 초과 단가는 저장 $0.015/GB-month, A $4.50/100만 회, B $0.36/100만 회이며 인터넷 전송량 자체의 요금은 없다. 저장·작업량의 과금 단위는 올림 계산한다. [Cloudflare R2 공식 요금](https://developers.cloudflare.com/r2/pricing/)

현재 6.12GB가 한 달 내내 유지되고 **평균 10MB 사진**을 추가해 한 달 내내 보관한다고 가정한 R2 저장료 예시다. 작업 요청 비용은 포함하지 않았다.

| 추가 사진 | 계정 전체 저장량 | 월 저장료 추정 |
|---:|---:|---:|
| 1,000장 | 16.12GB | 약 $0.11 |
| 10,000장 | 106.12GB | 약 $1.46 |
| 20,000장 | 206.12GB | 약 $2.96 |

현재 무료 저장량 여유는 약 3.88GB, 10MB 사진 기준 약 388장이다. 실제 저장 요금은 월간 평균 보관량에 따라 달라지므로 월말에 추가한 파일은 한 달 내내 저장한 예시보다 적게 계산된다.

## 열람이 많아지면

현재 native 사진 응답은 `no-store`이고 별도 Cache API를 쓰지 않는다. 사진 GET마다 Worker를 거쳐 D1에서 연결 정보를 조회하고 R2에서 파일을 읽는다. 따라서 사진이 많은 글은 열람 한 번에 여러 요청이 발생한다.

대략 본문 요청 1회 + 관리자 세션 확인 약 1회 + 사진 N회 + 기타 정적 요청이다. 정적 요청도 현재 Worker를 먼저 거치는 구성이다. 조회수 기록은 본문 요청 안에서 D1에 처리하므로 별도의 HTTP 요청을 추가하지 않는다.

- **지금 먼저 고려할 한도는 Workers Free의 계정 전체 하루 100,000요청이다.** 이를 넘으면 요청 오류가 발생하며 자동으로 유료 전환되지는 않는다. 사진 10장이 있는 글에 본문·세션 요청을 합쳐 12회만 잡으면 다른 트래픽 전에도 하루 약 8,300회 열람 정도다. 정적 파일·다른 글·관리자·계정 내 다른 서비스 요청을 빼지 않은 단순 상한 계산이며 보장 방문자 수가 아니다. [Workers 일일 요청 제한](https://developers.cloudflare.com/workers/platform/limits/#daily-requests)
- D1 Free에는 하루 읽은 행 500만 개·쓴 행 10만 개·저장 5GB 제한이 있다. SQL 호출 한 번이 읽거나 쓰는 행 수는 쿼리에 따라 다르므로 SQL 요청 수와 행 수를 같게 계산하면 안 된다. [D1 공식 요금](https://developers.cloudflare.com/d1/platform/pricing/)
- R2 사진 GET만 계산하면 월 100만 회와 1,000만 회는 무료분 안이고 2,000만 회는 약 $3.60이다. 이는 R2의 Class B 요청만의 예시이며 다른 Class B 작업도 합산된다. 현재 Workers Free의 일일 한도는 별도로 적용되므로 이 금액만으로 해당 트래픽을 처리할 수 있다고 보장하지 않는다. [R2 공식 요금](https://developers.cloudflare.com/r2/pricing/)

향후 Workers Paid를 선택하면 최소 월 $5에 요청 1,000만 회와 CPU 시간 3,000만 ms가 포함되고, 초과 요청은 $0.30/100만 회, 초과 CPU는 $0.02/100만 ms다. R2·D1 등 별도 제품의 사용 요금까지 모두 포함하는 정액제는 아니다. 현재 유료 전환은 하지 않았다. [Workers 공식 요금](https://developers.cloudflare.com/workers/platform/pricing/)

현재 수준에서는 사진 원본 저장량보다 사진별로 발생하는 요청과 무료 일일 한도가 먼저 중요해질 수 있다. 다음 비교는 압축 정책을 검토하기 위한 설명이며 압축·리사이즈·캐시 기능이나 요금제를 변경하지 않았다.

## 이관 사진은 지금 올린 사진보다 작은가

아래 전체 통계는 **로컬 이관 보존본의 이미지 헤더·메타데이터를 집계한 과거 자료 기준**이다. 이번 현재 운영 전체 사진을 재조회한 결과가 아니며 공개·비공개 이관 보존 파일의 합계다. GIF·SVG·ICO·동영상은 제외한 정적 래스터 이미지이고 사진·화면 캡처·도표는 따로 분류하지 않았다. 같은 사진의 다른 크기 파일이 별도로 포함될 수 있으므로 파일 수를 고유 사진 수로 단정하지 않는다. MB·GB는 십진 단위로 표시한다.

| 이관 보존본 구분 | 파일 수·합계 | 파일 크기 중앙값 / 90백분위 | 긴 변 중앙값 / 90백분위 |
|---|---|---|---|
| 네이버 정적 이미지 전체 | 4,673개·2.267GB | 236.5KB / 1.145MB | 930px / 1,932px |
| 네이버 플랫폼 자산 313개를 제외한 소유 사진류 | 4,360개·2.254GB | 254.2KB / 1.165MB | 966px / 1,932px |
| 티스토리 정적 이미지 | 813개·1.286GB | 766KB / 3.398MB | 2,608px / 4,096px |

90백분위는 해당 값 이하가 약 90%라는 뜻이다. 네이버 소유 사진류는 1MB 초과 17.2%·5MB 초과 0%(최대 4.749MB), 티스토리는 1MB 초과 44.3%·5MB 초과 5.4%(최대 17.359MB)였다. 티스토리 정적 이미지 중 긴 변 3,840px를 넘는 파일은 46.5%였다. 이관 사진을 모두 작은 해상도로 일괄 축소했다고 볼 수는 없다. 네이버 자료는 보존된 파일 기준으로 대체로 해상도가 작고, 티스토리는 큰 해상도를 유지하면서 파일이 작게 압축된 사례도 있다.

이번 운영 공개 표본을 새로 읽은 결과는 다음과 같다. 운영 DOM의 사진 해상도와 해당 로컬 파일의 메타데이터·바이트를 대조한 표본이며 전체 운영 사진에 일반화하지 않는다. 운영 파일 전체를 다시 내려받아 해시까지 전수 대조한 검사는 아니다. 이관은 원본 플랫폼에서 받은 바이트를 그대로 보존한 것이며 최초 카메라 원본과 같다고 단정하지 않는다.

| 현재 공개 표본 | 확인한 해상도 | 파일 크기 |
|---|---|---|
| #575 티스토리 사진 7개 중 JPG 6개 | 4,080/4,096 × 3,072px | 각각 261,705·369,409·342,323·336,077·298,851·441,685바이트(약 0.26~0.44MB) |
| 같은 글 PNG 1개 | 3,000 × 2,250px | 6,300,911바이트(약 6.30MB) |
| #1 네이버 PNG 4개 | 930 × 620px | 각각 1,053,504·1,243,089·979,417·1,069,488바이트(약 0.98~1.24MB) |
| #600 새 사진 9개 | 3,072 × 4,080/4,096px 또는 가로·세로 교차 | 앞선 이번 업로드 메타데이터는 합계 약 93.6MB·평균 약 10.4MB. 개별 업로드 경로와 현재 사진의 일대일 대조는 하지 않았다. |

따라서 픽셀 수가 비슷해도 JPG/PNG 형식, 압축률과 사진 내용에 따라 파일 크기는 크게 다르다. #600과 비슷한 약 1,250만 화소인 이관 JPG 표본도 훨씬 작지만, 그 수치를 모든 새 사진의 달성 가능 용량이나 같은 화질 보장으로 사용할 수는 없다.

## Google 포토의 저장용량 절약 수준과 비교

Google은 저장용량 절약 모드에서 사진을 압축하고, 1,600만 화소를 넘는 사진은 1,600만 화소로 줄인다고 설명한다. 일부 사진은 압축할 수 없을 수 있다. 사진당 고정 MB나 인코더 품질값·알고리즘은 공개하지 않으므로 이 블로그가 Google과 완전히 같은 결과를 낸다고 정할 수는 없다. [Google 포토 공식 백업 화질 안내](https://support.google.com/photos/answer/6220791?co=GENIE.Platform%3DDesktop&hl=ko)

현재 #600 사진은 약 1,250만 화소여서 **1,600만 화소 상한만 적용하면 해상도가 줄지 않는다.** 용량을 줄이려면 같은 해상도에서 재압축하거나 별도의 더 낮은 해상도 기준을 정해야 한다. 예를 들어 기본 최대 1,600만 화소와 재압축을 조합하는 설계는 가능하지만, 실제 사진으로 화질과 크기를 비교하기 전에는 평균 1~3MB 달성을 확정할 수 없다. 글씨가 있는 화면 캡처·투명 이미지·움직이는 사진 등은 일반 사진과 형식 보존 조건도 다르다.

## 새 사진을 압축한다면 비용과 한도는

기존 6.12GB는 **앞선 2026-09-23 조회값을 그대로 사용하는 가정**이며 이번 비교에서 R2 전체 용량을 다시 조회하지 않았다. 기존 사진은 그대로 두고 새 사진 1만 장을 한 달 내내 보관할 때의 저장료만 비교한다. 새 사진을 업로드 전 사용자 브라우저에서 축소·재압축하고 압축본만 R2에 저장하는 방식을 가정한다. Cloudflare Images 같은 유료 변환 서비스를 사용하지 않는다면 별도 변환 서비스 요금은 발생하지 않지만 실제 정책·형식 호환성과 품질은 구현 전에 실제 사진으로 시험해야 한다. 평균 1~3MB는 Google의 확정 수치가 아닌 비교 시나리오다.

| 새 사진 평균 | 1만 장 추가 후 전체 | 월 R2 저장료 추정 | 현재 무료 여유 3.88GB에 들어가는 새 사진 |
|---:|---:|---:|---:|
| 10MB | 106.12GB | 약 $1.46 | 약 388장 |
| 3MB | 36.12GB | 약 $0.41 | 약 1,293장 |
| 2MB | 26.12GB | 약 $0.26 | 약 1,940장 |
| 1MB | 16.12GB | 약 $0.11 | 약 3,880장 |

10MB를 기준으로 3/2/1MB는 용량이 70%/80%/90% 줄어드는 가정이다. 실제 최근 업로드 평균 약 10.4MB와 비교하면 약 71~90% 감소에 해당한다. 이 표는 새 사진 한 장당 저장 파일 한 개 기준이며 원본과 압축본을 모두 R2에 보관하면 원본 용량도 더해야 하므로 표의 저장 절감 예상은 성립하지 않는다. 원본 보관 여부와 사진 형식별 처리는 구현 전에 정할 별도 설계 사항이다.

사진을 작게 만들면 다운로드 데이터와 로딩 시간이 줄 수 있지만 **같은 사진 수라면 Worker 요청 수·R2 GET 수·D1 조회 행 한도가 압축 비율만큼 늘어나지는 않는다.** 위에서 설명한 요청·행 제한은 그대로다. R2 인터넷 전송 자체는 무료이므로 이 경우 주된 효과는 저장 여유와 로딩 부담 개선이며, 조회 비용까지 같은 비율로 절감한다고 계산하지 않는다.

이번 답변은 크기 비교·정책 설명·예산 추정까지다. 신규 압축 기능은 구현하지 않았고 기존 사진·원본·작업본·공개 내용도 수정하지 않았다.

## 추가 검토: 기존 PNG와 클립보드 사진의 JPG 저장

사용자는 일반 사진을 PNG로 보관하는 비효율을 줄이기 위해 기존 블로그 사진의 JPG 변환과 신규 첨부·클립보드 붙여넣기도 JPG로 저장하는 공통 처리 가능성을 검토하도록 요청했다. 최신 운영 #600 DOM의 사진 9개는 저장 주소 확장자상 모두 JPG였다. 사진 헤더 바이트로 실제 MIME까지 다시 검증한 것은 아니지만 평균 약 10.4MB의 원인을 PNG 때문이라고 단정할 수 없다. JPG 형식 변환만으로 해결되는 문제가 아니므로 기존 JPG 입력의 재압축 기준도 함께 검토한다. 형식별 보존본 집계와 입력 경로 검토를 마쳤으며 기능 구현이나 실제 사진의 일괄 변환은 하지 않았다.

이관 정적 이미지 전체에서 PNG는 1,703개·1.458GB로 정적 이미지 총 3.553GB의 약 41.0%였다. 이는 공개·비공개 로컬 이관 보존본 기준이며 현재 운영 변환 대상 수가 아니다. 네이버 소유 사진류는 JPG 3,308개·1.335GB와 PNG 1,052개·919.5MB, 티스토리는 JPG 450개·759.1MB와 PNG 362개·526.8MB였다. 서로 다른 사진 집합이므로 형식별 크기 차이를 같은 사진의 JPG 변환 절감률로 간주할 수 없다.

일반적인 불투명 사진은 JPG 재압축 후보가 될 수 있지만, 투명 배경·화면 캡처·도표·애니메이션은 보존해야 할 특성이 달라 예외를 구분해야 한다. 모든 PNG를 사진으로 단정하거나 무조건 JPG로 바꾸지 않는다. 코드에서 신규 파일 첨부와 클립보드 입력이 공통 `uploadImage` 경로로 이어짐을 확인했다. 파일 바이트 읽기와 SHA-256 계산 직전에 판별·압축을 적용하면 두 입력 경로에 같은 규칙을 적용할 수 있다. 이는 구현 위치 검토 결과이며 현재 파일 바이트를 바꾸는 코드는 추가하지 않았다. 브라우저의 `canvas.toBlob()`은 JPEG 형식과 품질값을 지정할 수 있지만 구체적인 품질·메타데이터·형식 호환성은 실제 입력으로 시험해야 한다. [MDN toBlob 문서](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/toBlob)

기존 사진을 실제로 전수 변환하려면 그 시점의 최신 운영 전체 목록·반영본·작업본에서 대상을 확정해야 한다. 이 문서의 이관 보존본 집계를 현재 변환 대상 목록으로 대신하지 않는다. 원본 key를 덮어쓰지 않는 새 key 방식과 비공개 자료·미공개 작업본 보호를 검토하며, 원본도 R2에 함께 남기면 앞선 압축본만 보관하는 저장 절감 예시는 성립하지 않는다. 원본 보관·공개 반영 정책을 이번 검토만으로 변경하지 않는다.
